# Whole-loop runtime proof

This is a prospective engineering check of `FoundationLoop`, not a learning
experiment. It is prepared independently of the live foundation pilot and must
not run on the GPU until the parent task explicitly authorizes it. Existing
trainer-only execution proofs do not establish complete controller behavior.

The model is the unchanged sequence model with width 192, four layers, four
heads, feedforward width 768, maximum 12 turns, model seed 8301, and AdamW learning
rate 0.001. Each update contains three 32-episode family microbatches. The strict
local execution profile is configured before CUDA initialization; preparation
freezes its exact runtime, source closure, canonical data and zero-update loop
envelope. Evaluation uses six 32-episode banks: all three domains in both
development and retention, with 8, 10 and 12 turns represented. Replies are
generated by the provider's existing teacher-free evaluator.

The fresh fixture plan uses seed 831000001, ordering seed 0, six ten-update depth
stages, a six-update common tail, and rehearsal every second slot. Only its first
eight mixed-order updates are executed. Their lengths include 8, 10 and 12 turns.
The original color pair zero in each executed bundle is reserved and repaired
through the existing authenticated naming-only admission mechanism. Thus both
sides of the practice interruption encounter the admitted path. Original
procedure and value recipes remain unchanged. Evaluation transcripts are also
protected against the complete finite training plan before a learner is built.

Five separately launched, one-shot workers run in this order:

| Worker | Operations | Updates |
| --- | --- | ---: |
| Uninterrupted | Save one baseline bank; finish baseline and train three; train five and finish endpoint evaluation | 8 |
| Partial evaluation | Save exactly one baseline bank | 0 |
| Split practice | Reload partial evaluation; finish baseline and train three, leaving the eight-update request pending | 3 |
| Resumed | Reload the pending request; train five and finish endpoint evaluation | 5 |
| Repeat | Repeat the uninterrupted path from the same initialization in a new process | 8 |

The prescribed total is 24 optimizer updates and 2,304 training episode
exposures. The three complete trajectories each score baseline and endpoint:
36 banks and 1,152 evaluation episode exposures. These are planned quantities;
the verifier must reconcile them against recorded chunk and step reports,
canonical bundle identities, actual bytes/exposures and checkpoint counters.
An occupied or interrupted directory is preserved, and no command automatically
retries. Started operations without completed reports remain unknown physical
work and cannot produce a passing proof.

Comparison includes full optimizer tensors, learner evidence, pending requests,
partial evaluation positions/results, retention references, bounded history and
controller counters. Independently executed trajectories may differ only in the
explicit learner, committed-work and schema-qualified response timers, including
each response bank's scorer `seconds`. Immediate
reload equality includes those timers too. Every ignored time must be finite
and nonnegative; nested timing scopes remain checked. No general suffix-based
field filtering is used.

Actual `FoundationLoop.load` calls occur in the CUDA workers. The final verifier
is CPU-only: it restores each learner through the actual `FoundationTrainer`,
revalidates controller and metric evidence against canonical banks, and compares
the recorded CUDA envelopes without fabricating a CPU provider identity. It
performs no neural forward pass or optimizer step. Sources, artifacts, journal
chains, runtime identities and separate process identities must all agree.

Worker wall time includes setup, restoration, scoring, training and durable
writes; operation/component timers are nested subsets and must not be summed
again. CPU verification is reported separately. The endpoint is the end of an
eight-update **window**, not exhaustion of the 66-update plan. Existing CPU tests
cover finite-plan exhaustion. Passing would demonstrate only this local,
source-bound whole-loop execution; it implies neither broad learning ability,
automatic checkpoint promotion, nor repeatability on other workloads or devices.
