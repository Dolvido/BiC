# Computer-use proof of concept

This experiment tests whether Brain in Computer can learn **restricted English instructions and short replies while operating a small visual interface**. The user has now authorized this training. The earlier v0.2 prohibition on English training describes that earlier development stage; it does not prohibit this experiment.

This document specifies scope and evaluation. Measured outcomes belong in the results record linked below. The existence of this design does not establish successful learning.

## The environment and learning problem

The task environment is a controlled desktop rendered in Python with Pillow at 96 × 96 pixels. It contains four colored buttons in randomized layouts, a text field, and visible feedback. The model receives a 32 × 32 RGB rendering, the English prompt, and declared cursor, focus, and elapsed-step signals. Actions are restricted to the implemented pointer clicks, `h`, `i`, `o`, `k`, backspace, and stop.

A local browser interface displays the same simulated desktop and the model's behavior. It is a viewer and interaction surface for this application. The model is not navigating arbitrary browser pages, reading a DOM, controlling Windows, or operating external accounts.

| Task family | Intended behavior |
|---|---|
| Click a color | Locate the requested color despite its changing position and click it. |
| Click a position | Follow a spatial instruction regardless of which color occupies that position. |
| Describe a position | Produce a short reply naming the color shown there. |
| Type `hi` or `ok` | Focus the field, enter the requested sequence, and stop. |
| Ask about the last click | Read the visible last-color swatch and report that color. |
| Greet | Produce a short learned greeting. |
| Clarify | Produce a short learned clarification response for the supplied ambiguity examples. |

The last-click task is deliberately observable from the screen. Solving it does **not** establish hippocampal recall. Greetings and canonical clarification examples likewise demonstrate a narrow response repertoire, not unrestricted conversation or a general ability to recognize uncertainty.

Procedural teachers generate demonstration actions, target replies, and visual naming annotations. The trainer first samples an action class with explicit probabilities, then selects a demonstration state within that class. The first stage used equal probabilities across the 11 actions. Refinement uses stop probability 0.35 and probability 0.065 for each other action. Only action examples contribute action loss; completed reply examples do not contribute additional stop labels. These sampling choices control the contribution of stop examples to the action objective.

Reply learning uses supervised next-byte cross-entropy with eightfold weight on the first byte and bytes immediately following spaces. The aim is to emphasize word choices that distinguish colors and intents. A separate linear readout from the core visual region predicts 42 logits grouped into four button-color classifiers, a five-class last-click swatch classifier, and a 21-class text-field classifier. The mean visual classification loss receives weight 0.5; next-observation prediction retains weight 0.03. Action loss has weight 1. The word-weighted text loss has weight 1 in the first stage and 3 in refinement. These are engineered supervision choices, not proposed biological learning rules.

Visual annotations enter training losses only. The auxiliary visual logits are never fed to the policy or response generator. At evaluation and during an interactive session, actions come from the model and generated replies condition on their own previously generated bytes. There is no teacher policy, target reply, or scene annotation supplied to the inference path. This is supervised learning, not reinforcement learning or autonomous discovery of a computer interface.

## Biological inspiration and its limits

The design couples sensory processing, language, association, maintained goals, action selection, and feedback through the existing regional system. Human language involves interacting frontal and temporal networks with overlapping functions; our module names are functional analogies rather than an anatomical reconstruction. [Fedorenko, Piantadosi, and Gibson](https://colala.berkeley.edu/papers/fedorenko2024language.pdf)

| Implementation component | Biological inspiration and boundary |
|---|---|
| Pixel CNN and visual regional network | Hierarchical visual processing; supervised visual naming gives this pathway a direct objective. The CNN is an additional trainable frontend, not evidence that the original visual region alone learns pixels. |
| Byte-sequence English encoder and reply decoder | Temporal/frontal language processing; byte encodings and separate decoder modules are engineering choices. |
| Parietal association and thalamic routing | Integrate signals and select information for downstream processing. |
| Prefrontal recurrent state | Maintain instructions and task context across action steps. |
| Basal-ganglia and motor pathways | Select and produce discrete interface actions. |
| Hippocampal and cerebellar pathways | Candidate contributions from memory and prediction; usefulness must be measured. |
| Remaining sensory/modulatory regions | Retain the core's structure; absent auditory input and abstract modulation do not demonstrate hearing, emotion, or physiological regulation. |

The core contains 13 regional modules, with four additional interface networks for pixels, comprehension, production, and the semantic bridge. The auxiliary scene readout belongs to visual supervision rather than constituting a new anatomical region. Executing all modules does not show that every region is necessary or even trained by the selected losses. Inspect gradient reachability, unused heads, outgoing messages, and behavioral interventions. The next-observation head has an auxiliary loss; that alone does not demonstrate a useful world model or planner. Value and unused recognition heads must not be credited with learning from objectives that do not reach them. End-to-end backpropagation remains an engineering training method.

## Experimental protocol

1. **Record the experiment.** Preserve configuration, random seeds, parameter counts, software version, training updates, elapsed time, device, checkpoint identity, and evaluation script. Distinguish newly trained weights from inherited weights.
2. **Separate learning and assessment.** Use independent random streams for training scenes, validation, and final testing. Choose hyperparameters and stopping decisions with validation. Reserve final test results for assessment; any repeatedly consulted split becomes development evidence.
3. **Evaluate closed-loop actions.** Reset to a fresh scene, let the model act, render the resulting scene, and repeat until stop or the step limit. Do not correct wrong actions with teacher moves. Score environment outcomes, not just next-action agreement on demonstrations.
4. **Separate generalization conditions.** Report fresh scenes with familiar wording, held-out wording, and the combined layout/appearance shift separately. The shift moves button rectangles by up to two pixels, changes the background, and slightly alters button colors. These are bounded distribution changes, not evidence of transfer to unfamiliar applications. Note whether the shift remains distinguishable after downsampling. The trainer's final `validation_eval.json` uses `split=train` with fresh scene seeds; the CLI's `--split validation` selects a different, held-out template set.
5. **Score actions and language separately.** Report task success, stopping failures, typing completion, exact reply accuracy, and joint success where both matter. Teacher-forced token accuracy may diagnose training but cannot substitute for free-generation results. Include per-task counts and confidence intervals; label a single-seed result as such.

## Controls against shortcuts

Keep task identifiers, target colors, correct coordinates, teacher actions, and target replies outside model observations. The procedural generator and scorer may access hidden state; the inference model may access only the declared observation contract. Prompt and reply padding must not reveal a target. The elapsed-step signal can support action sequencing, so it is a declared simplifying cue.

Randomize color-position assignments and balance requested targets. Evaluate the same prompt on scenes requiring different answers, and different prompts on the same scene requiring different actions. Compare blanked or shuffled pixels and shuffled prompts against intact inputs. Otherwise a language classifier, fixed click location, or default sentence could imitate success without integration.

For typing, familiar strings and elapsed steps can support a memorized action sequence. Report that limitation even if completion is perfect. For descriptions, inspect whether position-specific pixel shortcuts survive changed layouts. For replies, audit how many distinct templates and factual combinations are actually tested.

Regional lesions establish sensitivity at inference time; parameter-matched and retrained comparisons are needed before claiming an advantage from biological partitioning. Hidden-state memory tasks, novel names, longer interactions, broader keyboards, and more varied layouts are subsequent experiments.

## Repeating the training stages

The release model inherits 5,000 updates from the first stage, then receives 4,000 refinement updates. All model weights remain eligible for optimization in both stages; “perception stage” names an artifact, not a visual-only or frozen-language training phase. Stage records must be interpreted together. The earlier discarded 2,500-update attempt is development evidence and does not contribute weights to this lineage.

From the project directory, using the installed Python environment, repeat refinement from the **included actual first-stage weights**:

```bash
python -m brain_in_computer computer-train --steps 4000 --initialize-from runs/computer-development/perception-stage.pt --stop-fraction 0.35 --language-weight 3 --seed 31 --threads 1 --output runs/repro-final
```

To rerun the two-stage configuration from random initialization:

```bash
python -m brain_in_computer computer-train --steps 5000 --stop-fraction 0.09090909090909091 --language-weight 1 --seed 31 --threads 1 --output runs/repro-stage1
python -m brain_in_computer computer-train --steps 4000 --initialize-from runs/repro-stage1/checkpoint.pt --stop-fraction 0.35 --language-weight 3 --seed 31 --threads 1 --output runs/repro-final
```

Other defaults are 2,100 procedural demonstration episodes, batch size 32, and learning rate 0.001. Refinement starts a new AdamW optimizer and resets sampling rather than continuing optimizer/RNG state. Its `step` field counts refinement updates only; the initialization record identifies inherited updates and a source checkpoint digest.

The original first stage sampled equal-probability action classes with `torch.randint`. The released trainer samples with `torch.multinomial`, which consumes randomness differently even with equal class probabilities. The from-scratch commands therefore reproduce the intended configuration and objective, not an exact numerical replay of the original first stage. Using the included `perception-stage.pt` preserves its actual weights. Cross-version, device, and numerical differences may still affect a rerun. Preserve distinct output directories; `computer-train` overwrites files in its output directory.

The original stage record is `perception_stage.json` (archive reference: `../runs/computer-development/perception_stage.json`). The final-stage record is `report.json` (archive reference: `../runs/computer/report.json`). Refer to [COMPUTER_RESULTS.md](COMPUTER_RESULTS.md) for measured outcomes and checkpoint identities.

## Interface verification

Run the local HTTP integration checks against the saved policy with:

```bash
python experiments/check_computer_ui.py --checkpoint runs/computer/checkpoint.pt --output experiments/computer_ui_verification.json
```

The script exercises the HTML endpoint, visible-state responses, real model turns, manual click/key events, and invalid-input handling. It records observed replies and actions without assuming every instruction succeeds. Cloud-browser access to this loopback interface was blocked with `ERR_BLOCKED_BY_CLIENT`; passing HTTP checks does not establish that browser layout or interaction rendering was visually verified.

## Path toward richer computer use

[MiniWoB++](https://github.com/Farama-Foundation/miniwob-plusplus) provides established web-interaction environments for later external evaluation. [From Pixels to UI Actions](https://arxiv.org/abs/2306.00245) investigates screenshot-driven instruction following with mouse and keyboard actions. These motivate a future migration from this controlled desktop to richer interfaces. The present experiment does not reproduce their architectures, training, task suite, or benchmark results.
